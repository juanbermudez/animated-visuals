Example · a paper, explained

Put the prompt in a variable, and a model can work through inputs 30 times longer than it can read

A visual guide to Alex L. Zhang, Tim Kraska and Omar Khattab, “Recursive Language Models”, arXiv:2512.24601, version 2, January 2026 · the paper · the code. Built with Animated Visuals; every number is from the paper and says where it comes from.

Give a model 1,000 documents and ask who won a beauty pageant mentioned in one of them. It can't even take the question: the documents are about 8.3 million tokens, roughly 30 times what GPT-5 reads at once. Now give it a Python session where those documents sit in a variable. It can search them, pull out the one that matters, and ask a copy of itself to read just that one. That is a Recursive Language Model, and this guide follows that one question all the way through.

The prompt is something to look at, not something to read

A model's window is how much text it can read at once. For GPT-5 that is 272K tokens (the paper's Fig. 1). The question's 1,000 documents come to about 8.3M tokens (App. E.1), so a base model can't take them: in Table 1, base GPT-5 scores 0.0 on this task, marked as running into its input limit. And inputs that do fit still suffer from what the paper calls context rot: quality drops as the prompt gets longer (§1).

An RLM never puts the input in the window. It starts a Python session, stores the input in a variable named context, and tells the model only what kind of thing context is and how long its pieces are (App. C.1). The window stays almost empty; the input is all there, one variable away. Switch between the two below, and pick a smaller input in settings to see one that fits.

The loop: write code, run it, look at a little

The model in charge is the root model. Each turn it writes a bit of code, the session runs it, and only a short, cut-off printout comes back into the root's window (§2). The code can do anything Python can, plus call one extra function, llm_query, which sends any string to another model and returns its answer. That is a sub-call. In the paper's GPT-5 runs the root is GPT-5 and sub-calls go to GPT-5-mini (§3.2). Results land in variables, not in the root's window. The loop ends when the root writes FINAL(answer), or FINAL_VAR(name) to hand back a variable (App. C.1).

Three choices separate an RLM from an agent with tools

Coding agents and retrieval agents also run code and call models. The paper sets its loop (Algorithm 1) beside a look-alike (Algorithm 2) and names the three places where the look-alike goes wrong (§2):

ChoiceAn RLMThe look-alike
Where the prompt livesIn a variable; the model gets a handle and a lengthIn the model's window, so it hits the window's limit and falls back to summarizing
Where the answer comes fromCan be a variable, so it can be longer than anything one call could writeThe model writes it out, so it can't be longer than one call's output
How sub-calls happenFrom code, inside loops, on pieces the code picked: one per line if that's what it takesAs an action the model spells out by hand, a few at a time

The model decides how to cut the input

Nobody tells the root how to split the work. Its instructions show a few example strategies and leave the choice to the model (App. C.1). The paper's appendix shows four real runs that cut very differently: for the pageant question it searched first and read one document; on a code repository it cut the input into big chunks and asked about each; on two counting tasks Qwen3-Coder labelled questions in batches in one run and one at a time in the other. The cut decides how many sub-calls happen. One thing all four share: recursion is one level deep. A sub-call is a plain model call, not another RLM (§6).

Long inputs, hard tasks

The paper's first figure pulls apart two things that usually get blurred: how long the input is, and how much of it the answer depends on (§3). S-NIAH hides one phrase in filler, so the work stays the same as the input grows. OOLONG asks for a count that depends on nearly every line: the work grows with the input. OOLONG-Pairs asks for pairs of entries: the work grows with the square of the input (§3.1). GPT-5 finds the needle at every length it can take, and it falls to almost nothing on the pairs task by 33K tokens. The RLM slides slowly and keeps going past GPT-5's window, to 1M tokens. Four tasks, against the usual tools

Table 1 lines the RLM up against the tools people already use: the base model; CodeAct, an agent that runs code but keeps the prompt in its window, given either a search tool (BM25) or sub-calls; a summary agent that summarizes whenever its window fills; and the RLM with its session but no sub-calls (§3.2).

With GPT-5 the RLM is best on all four. On BrowseComp+, the pageant question's task, it scores 91.3 against 70.5 for the summary agent, at $0.99 a query; the paper's linear estimate for GPT-5-mini simply reading all 6 to 11M tokens is $1.50 to $2.75 (Obs. 1). On OOLONG, which fits in the window, it beats the base model by 28.4% (56.5 against 44.0). On OOLONG-Pairs it scores 58.0 where the base model scores 0.1. Sub-calls earn their keep on the dense tasks: 56.5 against 36.0 without them on OOLONG, 58.0 against 43.9 on the pairs. Not always, though: with Qwen3-Coder, the version without sub-calls wins CodeQA (66.0 against 56.0) and BrowseComp+ (46.0 against 44.7) (Obs. 2). Switch the model.

The cost story is good on average and rough in the tail. With GPT-5, the median RLM run is cheaper than the median base-model call, but some runs go on for many turns and cost far more (the paper's Fig. 3, Obs. 4). Against the summary agent, which reads the whole input, the paper reports RLMs up to 3× cheaper (Obs. 4).

Training a small model to do it

Qwen3-8B, a small open model, barely works as an RLM out of the box. The authors fine-tuned it on 1,000 filtered RLM runs that Qwen3-Coder-480B produced on LongBenchPro, tasks unrelated to the four benchmarks (§3.2, App. A). The training is tiny by today's standards: 300 steps at a batch size of 64, 48 H100 hours (App. A). What made it cheap is that a sub-call is an ordinary model call, so only the root's job, driving the session, has to be learned (§3.2). Step through.

The paper sums this up as a 28.3% improvement (“on average” in the abstract, “a median” in the introduction). It also got cheaper: 1 to 4 cents a query instead of 3 to 19 (Table 1). And it passes base GPT-5 on three tasks, two of which GPT-5 couldn't fully take in; on OOLONG it trails, 32.0 against 44.0.

Where it struggles

The paper is candid about this (App. B, App. E):

  • It's slow. Every sub-call waits for the one before it, so the slowest runs take far longer than any baseline (§4, the paper's Figs. 7 and 8). Running sub-calls in parallel is left to future work.
  • Models differ a lot. On one OOLONG question Qwen3-Coder sent a sub-call per line, hundreds to thousands for one task, where GPT-5 makes “on the order of ten” (App. E). The authors added one line to Qwen3-Coder's instructions warning it off (App. C.1).
  • Telling an answer from a thought is brittle. In one OOLONG-Pairs run the model built the right list in a variable, kept re-checking it, then returned an answer it wrote itself, which was wrong (App. E.2).
  • Small inputs. On short inputs the base model is sometimes slightly better (Obs. 3), and small models without good coding skills struggle in the session at all (App. B).
