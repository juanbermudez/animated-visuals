Recursive language models

A visual guide to Alex L. Zhang, Tim Kraska and Omar Khattab, “Recursive Language Models”, arXiv:2512.24601, version 2, January 2026 · the paper · the code. Built with Animated Visuals. Every number is from the paper and says where it comes from.

Recursive language models (RLMs) let a model work with inputs longer than its context window by storing the prompt in a Python variable. The example asks who won a beauty pageant mentioned in one of 1,000 documents, about 8.3 million tokens or roughly 30 times what GPT-5 reads at once. The root model searches the variable and uses a sub-model call, a separate model request on selected text, to read the relevant document. This guide shows how the loop works, how it scales, its results on four tasks, and its limits.

The prompt as a variable

A model's context window is the text it can read at once. GPT-5's window is 272K tokens (the paper's Fig. 1). The example's 1,000 documents total about 8.3M tokens (App. E.1). A base model cannot take the full input. Base GPT-5 therefore scores 0.0 on this task in Table 1, marked as running into its input limit. Even when an input fits, the paper reports context rot, where quality drops as the prompt grows (§1).

An RLM stores the input in a Python variable named context instead of putting it in the model's window. It tells the model what context contains and how long its pieces are (App. C.1). The window holds a short description while the complete input remains available in the variable. Switch between the two models below, or choose a smaller input to see one that fits.

How the loop runs

The root model controls the loop. On each turn, it writes code. The Python session runs that code and returns a short, cut-off printout to the root model's window (§2). The code can use Python and one extra function, llm_query. This function sends a string to another model and returns the response. Each use is a sub-model call. In the paper's GPT-5 runs, GPT-5 is the root model and GPT-5-mini handles the sub-model calls (§3.2). The results stay in variables outside the root model's window. The root model ends the loop with FINAL(answer), or uses FINAL_VAR(name) to return a variable (App. C.1).

What separates it from an agent with tools

Coding agents and retrieval agents also run code and call models. The paper compares its RLM loop in Algorithm 1 with a similar agent loop in Algorithm 2 and identifies three differences (§2).

Design choiceAn RLMAn agent with tools
Prompt locationA variable; the model receives a handle and a lengthThe model's window; it reaches the window limit and falls back to summarizing
Answer locationA variable, so the answer can exceed one call's outputThe model's output, limited to what one call can write
Sub-model callsCode makes them inside loops on selected pieces, including one per line when neededThe model requests a few calls at a time as actions

How the model splits the input

The instructions show the root model several example strategies but do not prescribe how to split the work (App. C.1). Appendix E shows four different runs. For the pageant question, the root searches first and reads one document. On a code repository, it splits the input into large chunks and asks about each one. On two counting tasks, Qwen3-Coder labels questions in batches in one run and one at a time in the other. The split determines the number of sub-model calls. All four runs use one level of recursion. Their sub-model calls are regular model calls and cannot start another RLM (§6).

Scaling with input length

The paper's Fig. 1 compares input length with how much of the input the answer depends on (§3). S-NIAH hides one phrase in filler, so the work stays constant as the input grows. OOLONG asks for a count that depends on nearly every line, so the work grows with the input. OOLONG-Pairs asks for pairs of entries, so the work grows with the square of the input (§3.1). GPT-5 finds the phrase at every length it can take. Its score falls to almost nothing on OOLONG-Pairs by 33K tokens. The RLM declines more slowly and continues past GPT-5's window to 1M tokens. Results on four tasks

Table 1 compares the RLM with a base model; CodeAct, an agent that runs code but keeps the prompt in its window, with either the BM25 search tool or sub-model calls; a summary agent that summarizes when its window fills; and an RLM with a Python session but no sub-model calls (§3.2).

With GPT-5, the RLM scores highest on all four tasks. On BrowseComp+, the pageant question's task, it scores 91.3 against 70.5 for the summary agent at $0.99 a query. The paper's linear estimate for GPT-5-mini reading all 6 to 11M tokens is $1.50 to $2.75 (Obs. 1). On OOLONG, which fits in the window, the RLM improves on the base model by 28.4% (56.5 against 44.0). On OOLONG-Pairs, it scores 58.0 while the base model scores 0.1. Sub-model calls improve the dense tasks: 56.5 against 36.0 without them on OOLONG, and 58.0 against 43.9 on OOLONG-Pairs. With Qwen3-Coder, the version without sub-model calls scores highest on CodeQA (66.0 against 56.0) and BrowseComp+ (46.0 against 44.7) (Obs. 2). Switch the model to compare both.

Average cost does not show the most expensive runs. With GPT-5, the median RLM run costs less than the median base-model call. Some runs take many turns and cost much more (the paper's Fig. 3, Obs. 4). Compared with the summary agent, which reads the whole input, the paper reports RLMs up to 3× cheaper (Obs. 4).

Fine-tuning a small model

Qwen3-8B, a small open model, performs poorly as an RLM without fine-tuning. The authors fine-tuned it on 1,000 filtered RLM runs that Qwen3-Coder-480B produced on LongBenchPro, using tasks unrelated to the four benchmarks (§3.2, App. A). Training used 300 steps at a batch size of 64 and took 48 H100 hours (App. A). Each sub-model call is an ordinary model call, so only the root model had to learn how to manage the session (§3.2). It exceeds base GPT-5 on three tasks, including two that GPT-5 could not fully take in. On OOLONG, it scores 32.0 against 44.0.

Limits

The paper reports four limits (App. B, App. E).

  • Latency. Every sub-model call waits for the previous one, so the slowest runs take much longer than any baseline (§4, the paper's Figs. 7 and 8). Parallel sub-model calls are left to future work.
  • Model behavior varies. On one OOLONG question, Qwen3-Coder made one sub-model call per line, producing hundreds to thousands for one task. GPT-5 makes “on the order of ten” (App. E). The authors added one line to Qwen3-Coder's instructions to discourage this behavior (App. C.1).
  • Final-answer handling. In one OOLONG-Pairs run, the model built the correct list in a variable and kept checking it. It then returned a different answer that it wrote itself, and that answer was wrong (App. E.2).
  • Short inputs. The base model is sometimes slightly better on short inputs (Obs. 3). Small models without strong coding skills also struggle to use the session (App. B).
