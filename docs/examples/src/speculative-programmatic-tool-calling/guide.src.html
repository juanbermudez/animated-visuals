Start the tool calls before the model finishes the code

A visual guide to Alex L. Zhang, “Speculative Programmatic Tool Calling”, blog post, August 24, 2026 · the post · the code (MIT). Built with Animated Visuals; every measured number is from the post and says where.

Watch a code-writing agent and you'll notice the wait. The model types out a whole program, and only then does anything run. If line 2 asks a sub-model three questions, those questions sit there, fully written, while the model types the next four lines. Speculative programmatic tool calling (sPTC, Zhang's name for it) starts them right away. This guide follows one six-line program from the first token to the answer.

The program we'll follow

Zhang tested the trick on a Recursive Language Model (RLM), a harness where the main model never reads the long input directly. The input sits in a Python variable called context, the model writes code against it in a REPL (a Python session that keeps its variables from one cell to the next), and llm_query asks a smaller sub-model one question. His benchmark, OOLONG, asks for this kind of work: label a long list of items, then count the labels (its paper calls it classification and counting in context). Here is one cell the model might write.

chunks = context.split("\n\n")                             # 1  plain code
labels = [llm_query("Label: " + c) for c in chunks[:3]]    # 2  three sub-calls
tally = llm_query("Count the labels: " + str(labels))      # 3  needs line 2
notes = read_file("notes.txt")                             # 4  reads a file
review = llm_query("Compare with my notes: " + notes)      # 5  needs line 4
print(tally, review)                                       # 6

Five sub-model calls and one file read. The three label calls don't depend on each other. The tally needs all three labels. The review needs the file. Every figure below runs on these six lines.

Calls start while the model is still writing

Without speculation, the harness waits for the last line, then runs the cell top to bottom. Line 2 calls the sub-model three times in a row, because each call blocks until it returns. With speculation, the three label calls start the moment line 2 is complete, all at once, and the tally starts as soon as they come back, while the model is still writing. The saving has two parts, and the post names both. One is overlap: calls run during the writing instead of after it. The other is what Zhang calls a naive JIT compiler (a compiler that rewrites code while it runs): blocking calls that don't depend on each other run at the same time, even though the code wrote them one after another. In this turn, of the saving comes from running the labels at once and from overlapping with the writing.

A throwaway copy runs the half-written program

To start line 3's call early you need line 3's input, and that input is line 2's output. So the harness keeps a shadow copy: a deep copy of the program's variables that runs each line as soon as it's complete. In the copy, a tool call doesn't wait. It starts in the background and leaves a promise, a placeholder that fills in when the answer arrives. Each call is filed under its inputs in a store of early calls, so the real program can find it later.

The copy never touches the real variables, and it's thrown away at the end of the turn. Zhang keeps the two apart on purpose: the model may write broken code or stop in the middle of a call, and the real program should run the cell as one unit or not at all.

It only starts what it can prove is safe

Running half-written code is only fine if nothing it does can leak out. The post's rule has two parts. Tools are declared up front: @spec.tool(speculatable=True, pure=True) marks a tool that may run early and has no side effects, and a tool without those flags, like read_file here, never runs early. Ordinary functions that reach outside the program, like open, are marked unsafe too. Then any call whose inputs depend on something unsafe is not started.

Two details keep it honest. Calls are matched by their inputs and by how many times they occur, so five identical calls for a majority vote get five separate answers, not one answer reused five times. And a started call can still be thrown away: if the real program never asks for it, its answer is dropped. Pick a call and step through its life.

Notice what's missing: nothing ever needs rolling back. A wrong guess never reaches the real variables, so the worst a bad guess costs is a sub-call nobody uses. Those add up, though. Zhang's worst case is a serving engine clogged with extra speculative requests, which you control through how aggressive speculation is and how the calls are queued. The copy itself is cheap: per the post, checking the stream costs close to nothing, and the deep copy is small because REPLs tend to hold few large mutable objects.

When it pays

So how much can it save? In this program the overlap is capped by how long the model keeps writing after line 2, and running at once is capped by how many calls are independent. The gain is biggest when the calls just fit inside the writing: . Past that, the tally finishes after the writing does and the gain settles toward 5 ÷ 3 ≈ 1.67×, because five calls in a row became a chain of three. Drag the line. The band is what the post measured on a real benchmark, and it sits well below this toy's best case.

Measured: 1 to 1.2×, with a wide spread

Zhang measured it on his RLM harness with OOLONG (the trec-coarse split, 132k tokens of context) and OOLONG-Pairs (32k), served by vLLM on a node of eight H100s, using Qwen3-30B-A3B-Instruct. He ran each setting 5 times, at temperature 0.7 and at 0.0 (to cut the run-to-run variance), with 4 and with 8 tasks sharing the same serving engine. His summary: speed-ups of about 1 to 1.2×.

The plot behind that summary deserves a careful look. Speculation's mean wall time is lower in all four settings, and the ratio of the means is , more than his range. But the 95% intervals overlap in every setting. Switch to sub-calls: the speculative runs made more sub-calls in three of the four, so the two sides didn't take the same paths through the tasks, and the bars can't isolate the trick. Quote his 1 to 1.2×; read the bars as “probably faster, not precisely by how much”.

Why so far below the toy? The toy is one turn whose time is all calls. The benchmark tasks take about nine or ten turns each (the turns tab), 4 or 8 of them share one serving engine, and speculative calls add their own load to it. Zhang is upfront that the speed-up is hard to pin down: it depends on how slow the tools are, how many tokens the model generates, how loaded the serving engine is and which choices the harness makes.

Where it's worth it

Zhang's own read: the trick earns its keep when the tools are sub-models or sub-agents, because those are slow, and especially with models you run locally, where decoding one main context leaves the hardware waiting on memory and extra calls put it to work. Through a hosted API the only gain is overlap. He expects the bigger long-run win to come from smarter JIT-style tricks that overlap calls with the program's own execution, as harnesses write longer programs.
